apidrift

Stripe changed its API. This is the line in your code that breaks.

Install on GitHub

apidrift watches Stripe's published OpenAPI spec. When a release removes a field, retires an endpoint, or makes a new parameter required, it finds the call sites in your repository that send exactly that, and opens one issue with a link to each line. When Stripe documents a replacement, it also opens one pull request with the change applied. Nothing else: no digest of every change, no issue when you are unaffected.

Install on GitHub

Free while it is Stripe-only.

Four permissions: read and write access to code and pull requests, read and write access to issues, and the repository metadata GitHub requires of every App. What it writes is one branch and one pull request per repository; it never pushes to your default branch. apidrift downloads a snapshot of your default branch, reads it, and deletes it when the check ends. It never runs your code. It checks after each push to your default branch and whenever Stripe publishes a new spec.

How it works

  1. Stripe publishes spec3.sdk.json; apidrift keeps every version{% if stripe_latest %} (the latest it holds is {{ stripe_latest }}){% endif %}.
  2. Each release is diffed against the one your code last passed, release by release, so every finding names the release that introduced it.
  3. Your Python, JavaScript, TypeScript and Ruby are parsed for Stripe calls and the fields they send. Only the calls the diff touches are reported.
  4. When Stripe's changelog documents what to send instead (a field renamed, a field removed, or a value that changed shape), apidrift rewrites the request at every affected call site, re-scans the changed files to confirm they now send what the new release expects, pushes a branch named apidrift/stripe-<version>, and opens one pull request per repository. The pull request lists the API-version pins it found and asks you to merge it together with your API-version and SDK upgrade, because Stripe rejects renamed and reshaped fields on older versions (a removed field can go on any version). Merging stays a human click.

What it does not do yet

  • Pull requests only for changes Stripe's changelog documents a replacement for: renamed fields, removed fields, and fields whose value changed shape (today: payment_method_types, payto, filters.countries, billing_cycle_anchor), verified by re-scanning the changed files. Anything Stripe has not documented a replacement for (for example a new required field whose value only you know) still arrives as an issue.
  • Stripe only.
  • It does not read which API version your account is pinned to.
  • Calls whose arguments it cannot see are marked ? (possibly affected), not guessed.
  • Other languages get endpoint-level matches from literal URLs only.
